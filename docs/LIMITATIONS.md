# Limitations and validation status

[← Back to the README](../README.md)

AI Hat is in beta. Statuses below describe the current source and CI configuration. A source implementation is not evidence that a feature has passed on a physical phone; those checks remain explicitly marked.

## Resolved limitations

No limitations are marked **FIXED** yet. The changes below need native CI and device evidence before they can be marked resolved.

## Verified supported features

- **VERIFIED — Local chat model format and engine contract:** the local chat path accepts single-file GGUF models through `llama.rn` (llama.cpp); see `src/lib/local/engine.ts`, `src/lib/local/inference.ts`, `src/lib/local/catalog.ts`, and the `llama.rn` plugin in `app.json`. Current model discovery filters out split GGUF files and vision projectors.
- **VERIFIED — Marketplace data sources:** skills are read from publisher repositories/directories and the MCP tab uses the official MCP registry; see `src/lib/market.ts`. Model files are discovered from Hugging Face repository metadata; see `src/lib/local/catalog.ts`.
- **VERIFIED — Marketplace categories and drawer entry:** the marketplace exposes Skills, MCP, Extensions (the app's ready-made connector catalog), and Models on platforms with local model support; Marketplace and My Models are in `src/components/Sidebar.tsx`.
- **VERIFIED — Automation configuration:** `.github/workflows/ci.yml` defines TypeScript, lint, Expo CLI/Zod compatibility, Sidebar-to-Expo-Router route checks, local stream and model-runtime lifecycle, model/download safety, and MCP marketplace security tests, documentation checks, a high-severity dependency audit, Android native archive unit tests and debug/release APK builds, iOS simulator compilation, desktop tests, and skill-runner tests. These job definitions are source-checked here; native workflow runs are still pending. `.github/workflows/android-apk.yml` and `.github/workflows/ios-ipa.yml` define release artifacts when run.

## Partially supported features

- **PARTIAL — GGUF download lifecycle:** progress, pause, resume, cancel, size checks, storage reservations, GGUF signature validation, publisher SHA-256 verification when Hugging Face exposes it, and persisted task metadata are implemented in `src/store/localModels.ts`. GGUF transfers use a two-slot FIFO; queued jobs are persisted and restarted safely, while queued cancellation does not create a native task. New installs use byte-encoded owner/repository/file paths, avoiding flattened-name and case-insensitive filesystem collisions; indexed older installs keep their original locations so saved background-task destinations remain valid. `modelStorageSegments`, legacy-path resolution, iOS background completion acknowledgment, the transfer scheduler, and the `releases a loaded model before replacing its on-disk file` case are covered in `src/lib/local/download-core.test.mjs`. The installed-model index and download recovery records use staged JSON writes with restart recovery; the same tests cover commit and recovery windows. Expo restores explicitly paused task state. On startup, a full-size `.part` file is verified and installed if present; incomplete files are retryable from the beginning. Expo does not restore JavaScript `DownloadTask` state after process termination, so active-transfer recovery is not guaranteed across termination. Checksums are not available for all discovered model files.
- **PARTIAL — Android Phonon archive extraction:** extraction uses a zstd/tar stream and bounded buffers, caps metadata files before parsing, validates tar headers and publisher hashes for model/config files, reports extraction progress at a throttled rate of about 100 native-to-JavaScript events per model, serializes preparation, checks cancellation while reading and skipping entries, maps damaged-archive failures to recoverable errors, and stages output before install. The source archive remains until promotion succeeds. Synthetic unit cases cover progress throttling, fresh install and replacement, insufficient storage, cancellation, retry cleanup after interrupted staging, integrity failure, duplicate required members, damaged headers, incomplete and corrupt Zstd archives, oversized and empty archives, missing tar end markers, traversal, symbolic links, and a 16 MB fixture in `modules/phonon/android/src/test/java/expo/modules/phonon/PhononArchiveTest.kt`; they are configured in `.github/workflows/ci.yml` but have not run here. The previous implementation already streamed with 64 KiB buffers on an I/O dispatcher, so the original crash trigger is not established; no tombstone or device reproduction is available.
- **PARTIAL — Model marketplace metadata and versioning:** architecture, parameter count, license and publisher revision are displayed only when returned by Hugging Face metadata. File discovery and downloads are pinned to the reported commit; installed models retain that revision, and an update action appears when a newer revision is known. GGUF models without publisher revision metadata cannot be reliably version-compared; see `src/lib/local/catalog.ts`, `src/lib/local/market-core.mjs`, `src/app/market-model.tsx`, and `src/store/localModels.ts`.
- **PARTIAL — GGUF install integrity:** downloads check the GGUF magic header, preserve an existing model during promotion, unload the matching in-memory model before replacing its file, and persist explicitly paused task state for restart recovery. The promotion ordering is covered by `releases a loaded model before replacing its on-disk file` in `src/lib/local/download-core.test.mjs`; see `src/store/localModels.ts`. Network and process-restart scenarios have not yet been exercised on iOS or Android.
- **PARTIAL — iOS model downloads:** the app downloads files directly to app document storage through Expo FileSystem native download tasks and does not buffer multi-gigabyte files in JavaScript. Expo’s iOS implementation uses `URLSession`, follows native redirects, and rejects non-2xx responses; Android uses OkHttp and also rejects non-2xx responses in the installed SDK source. Completed background transfers defer the iOS session completion callback until JavaScript verifies and promotes the model; Expo caps that acknowledgment window at 25 seconds. Expo does not restore JavaScript task state after process termination. Explicitly paused task state can be restored after relaunch; an active transfer interrupted by termination is retried from the beginning. See [Expo FileSystem SDK 58](https://docs.expo.dev/versions/v58.0.0/sdk/filesystem/). The reported iPhone failure still requires simulator/device reproduction.
- **PARTIAL — Device fit estimates and context:** `src/lib/local/fit.ts` and `src/lib/local/fit-core.mjs` use reported total memory and model file size for conservative size/context heuristics. Before loading a GGUF, the app checks that estimate; Android also reads `ActivityManager.MemoryInfo` and iOS reads `os_proc_available_memory()` immediately before initialization through `modules/devicememory`. Both available-memory readings are point-in-time estimates; Android also provides a system low-memory flag. The `model fit remains unknown…`, `safe context tiers shrink…`, `device capacity recommendations…`, and Android/iOS model-load preflight cases in `src/lib/local/download-core.test.mjs` cover the policy. These checks cannot guarantee that a model will load. Android Phonon additionally checks available memory in its native module.
- **PARTIAL — Model lifecycle:** installed GGUF and Phonon models are visible and removable in the device manager; GGUF queues, transfers, verification, installation, and inference states are tracked, and Phonon download/extraction progress plus pause, retry, and cancellation controls are surfaced there. Runtime transitions are covered by `src/lib/local/model-runtime.test.mjs`; queue/recovery behavior is covered by `src/lib/local/download-core.test.mjs`; archive extraction cases are in `modules/phonon/android/src/test/java/expo/modules/phonon/PhononArchiveTest.kt`. GGUF and Phonon still use separate lifecycle stores; package versioning and a generic multi-file installer are not unified.
- **PARTIAL — Skills and MCP marketplace:** discovery and install flows exist for skills and remote MCP servers. Downloaded skill scripts run inside the app's restricted runner with explicit user confirmation; they are not arbitrary native extensions. MCP stdio servers are not runnable on phones.
- **PARTIAL — Extensions category:** this is a discover/manage view over the existing connector catalog, not a general third-party extension package installer. Only the listed connector types and their current authentication flows are supported.

## Known remaining limitations

### Platform-specific restrictions

- **OPEN — iOS installs are unsigned by default.** The IPA workflow can sign when repository secrets are configured; otherwise sideloading requires a signing tool and the user's Apple ID.
- **OPEN — Android is supported for arm64-v8a and x86_64 builds.** `llama.rn` 0.13.0-rc.8 does not build local inference for 32-bit Android ABIs; release and CI workflows now restrict native builds to supported ABIs. Android is less exercised than iOS, and no successful current-run artifact has been observed from this workspace.
- **OPEN — Expo Go does not contain the app's custom native modules**, including llama.rn and Phonon. Use a development or release build.
- **OPEN — Live-text dictation** uses the platform speech service and its custom native module. In Expo Go the app falls back to its configured transcription endpoint.

### LLM engine limitations

- **VERIFIED — Primary local chat engine is `llama.rn`**, selected because it binds llama.cpp for React Native and directly supports the app's GGUF catalog on iOS and Android. The app currently enables Metal GPU layers on iOS when the setting is on; Android uses CPU inference. No Android GPU acceleration is claimed.
- **VERIFIED — Engine selection review:** ExecuTorch uses exported `.pte` LLM artifacts; LiteRT-LM uses its own model packaging; WebLLM targets browser WebGPU and MLC artifacts; Transformers.js uses ONNX models with browser WASM/WebGPU. They do not drop into the existing arbitrary GGUF/mobile catalog. The comparison and official references are in `docs/DEVELOPERS.md`.
- **OPEN — No alternative local inference provider is integrated.** A future provider must implement an explicit supported model format and pass iOS/Android build and device checks before models are offered for it.
- **OPEN — Models are text-only in the local chat path.** Images, tool execution by local models, multi-file GGUF shards, and unsupported formats are excluded or unavailable.
- **PARTIAL — Memory cleanup:** only one llama context is held at a time and it is released on backgrounding or after the configured idle interval. Closing an unfinished token stream now stops generation and drops late callbacks; the lifecycle gate is covered by `src/lib/local/generation-lifecycle.test.mjs`. Native stop timing and out-of-memory behavior still need device validation.

### Model format limitations

- **VERIFIED — Local chat downloads are single-file `.gguf` only.** The required engine is llama.cpp through llama.rn; download size is not a guarantee of runtime compatibility.
- **PARTIAL — Phonon speech model:** Android pins the publisher archive revision, checks its SHA-256 before extraction, then the native installer checks the extracted model/config hashes; iOS pins the Core ML repository revision and checks each package file's size and publisher SHA-256 using Expo FileSystem's native streaming digest. Tests cover checksum validation and Android archive payload validation. The model is English-only; Android requires 64-bit ARM and at least Android 8, while iOS requires iOS 18 or later. Published download sizes are about 164 MB for Android and 345 MB for iOS. Native build and device download/load/transcription behavior remain unverified here; see the physical-device test list.

### Marketplace limitations

- **OPEN — Metadata is consumed from external registries and publisher sites.** The app filters formats and validates some downloaded content, but does not authenticate every publisher's metadata cryptographically.
- **PARTIAL — Marketplace MCP configuration:** registry entries are bounded and restricted to known transports. Remote/source addresses require HTTPS without embedded credentials; secret URL variables, credential-like query parameters, invalid or reserved headers, and malformed auth templates are rejected. Nonsecret URL variables are escaped; auth tokens are always masked and stored through the secure keystore. These cases are covered in `src/lib/local/mcp-market-core.test.mjs`; general URL escaping is also covered in `src/lib/local/download-core.test.mjs`. Manually configured MCP connections retain their existing transport behavior, including local development endpoints.
- **PARTIAL — Marketplace and skill input bounds:** Hugging Face metadata JSON is capped at 8 MB and model-card text at 512 KB. Other registry JSON, website skill indexes, GitHub skill text, and skill files are byte-limited; website discovery and download URLs require HTTPS, and index metadata, checksums, and member paths are validated. Gzip expansion and tar/ZIP paths and sizes are bounded. Synthetic cases exercise secure site-origin parsing, bounded JSON, plain-tar/gzip-tar/ZIP routing, aggregate ZIP output limits, bounded streams, gzip expansion, tar checksums, truncation, invalid sizes, and traversal in `src/lib/local/download-core.test.mjs`; see `src/lib/market-safety.mjs`, `src/lib/local/market-core.mjs`, `src/lib/local/catalog.ts`, and `src/lib/market.ts`. React Native fetch implementations without response streams require a declared Content-Length for bounded reads.
- **PARTIAL — Extension packages are not supported.** The Extensions category manages only built-in connectors; there is no generic extension manifest, package-signing scheme, or sandbox for arbitrary native code.
- **OPEN — `skills.sh` discovery uses its currently public search endpoint** because it does not expose an unauthenticated app API. That endpoint may change; the other skill sources remain separate.

### Device and hardware limitations

- **OPEN — A successful download-size check cannot predict thermal throttling, memory pressure, or operating-system process limits.** Confirm model performance on each target device class.
- **OPEN — Phonon holds a large native model in memory.** The code checks broad device-memory thresholds, but physical-device load, transcription, background, and unload behavior have not been verified here.

### Build and CI limitations

- **OPEN — Production dependency audit still reports seven low-severity advisories through Expo Config's `deepmerge@4.3.1`.** `node-forge` is overridden to `1.4.2`; Expo CLI's Zod dependency is narrowly overridden to patched `4.6.7`, and `scripts/test-expo-cli-zod.mjs` exercises the CLI's actual schemas. The high-severity gate passes; npm offers no `deepmerge` patch and suggests an incompatible Expo SDK downgrade for that advisory. `.github/workflows/ci.yml` keeps `npm audit --omit=dev --audit-level=high` enabled.
- **PARTIAL — Android CI build:** `.github/workflows/ci.yml` installs API 37, Build Tools 37.0.0, and NDK 27.1.12297006 with SDK license acceptance, then verifies the llama.rn native-artifact marker, runs Android archive unit tests, builds arm64-v8a and x86_64 debug/release APKs, and uploads artifacts. The native-artifact skip is scoped to JavaScript-only jobs. `.github/workflows/android-apk.yml` installs the same toolchain for release APKs. This Chromebook has no configured Android SDK/NDK; an earlier local Gradle attempt also stopped on the unaccepted NDK license, so no native tests ran. GitHub Actions evidence is pending because this workspace has no authenticated GitHub CLI session.
- **PARTIAL — iOS CI build:** `.github/workflows/ci.yml` installs dependencies, verifies the llama.rn XCFramework marker, and defines an unsigned simulator build and app artifact job. This Chromebook has no Xcode, and the workflow has not run; GitHub Actions evidence is pending because this workspace has no authenticated GitHub CLI session.
- **VERIFIED — Expo configuration and dependency compatibility:** `npx expo-doctor` passed 20/20 checks for this working tree. `npx expo install --check` ran in offline mode and explicitly reported its compatibility result as unreliable, so it is not used as evidence.
- **VERIFIED — Continuous Native Generation prebuild:** `npx expo prebuild --no-install --clean` generated both Android and iOS projects from the app config. This validates plugin resolution but is not a native compile result.
- **VERIFIED — Platform JavaScript bundling:** under Node 22.23.4 on this ARM64 Chromebook, the latest `npx expo export --platform all --no-bytecode` generated web, iOS, and Android output; the Android and iOS JavaScript bundles are each about 4.9 MB. `--no-bytecode` validates JavaScript bundling only. The normal Android export reached Metro but Hermes bytecode generation failed because the installed `hermesc` binary is x86-64; Expo documents `--no-bytecode` for analysis only, not distribution. Native compilation and Hermes bytecode builds remain assigned to GitHub Actions.
- **OPEN — Signed distribution** requires Android keystore secrets or Apple signing secrets described in `.github/workflows/android-apk.yml` and `.github/workflows/ios-ipa.yml`.
- **VERIFIED — Supported local JavaScript toolchain:** Node 22.23.4 ARM64 is installed through nvm; TypeScript and Expo lint complete without the unsupported-Node warning. CI pins Node 22.
- **OPEN — The desktop application is not yet verified on physical macOS, Windows, or Linux desktop installations.** Linux Chromium and desktop backend checks are documented in `docs/DEVELOPERS.md`; app packages are unsigned and do not self-update.
- **OPEN — The web build needs the desktop app's local backend** and is not a hosted standalone website.
